# 音色库

零样本克隆用的**参考音频**与**原始素材库**。F5-TTS 和 GPT-SoVITS 共用这一套 ——
它们都靠"一段参考音频 + 那段音频的文字"决定音色，没理由各存一份。

**这个目录的内容不进版本库**（`.gitignore` 里只放行这份 README）。语音包动辄
1~2GB，一旦被 commit 就很难从 git 历史里清掉。换机器时照着下面的约定重建即可。

## 目录结构

```
voice-library/
  <人名>/
    default.wav + default.txt      ← 参考音频，引擎会把它列进音色下拉框
    calm.wav    + calm.txt         ← 语气变体
    teasing.wav + teasing.lab
    library/                        ← 原始素材库，引擎**不列**
      vo_xxx.wav + vo_xxx.lab
      战斗语音 - Battle/...
```

音色名就是 `<人名>`（用 `default`）或 `<人名>/<变体名>`。

## 「参考」和「素材库」必须分开

顶层那几条是参考，`library/` 是素材池。这个区分不是洁癖 —— 把 1291 条素材直接
当音色列出来，设置面板的下拉框就彻底没法用了（实测撞过）。

`library/` 是 [`tools/voices/organize.py`](../tools/voices/organize.py) 的**输入**。

## 为什么要有「语气变体」

零样本克隆每次**只用一条**参考音频，它不会把多条平均起来 —— 所以"同一个人的
一千条"本身不提升相似度。

但参考音频决定的不只是音色，**还有语气**：拿一条调笑的台词做参考，合成出来就是
调笑的语气；拿一条低落的，就是低落的。所以一个人该有几个语气变体，
让情感轴去选（心情低就用低落那条）。

## 加素材

### 只有音频、没有文字？（最常见）

`prep-voice-ref` 会**先裁到 8 秒，再用 Whisper 转写裁过的那一段** ——
所以文字天然和音频匹配。项目里已经有 whisper.cpp 和模型，不用再下东西。

```bash
cd src-tauri
cargo run --bin prep-voice-ref -- ~/某人.mp3 ../voice-library/某人/default 8
```

顺序很关键：**先裁再转写**。反过来做（先有整段的文字再去裁音频）会让文字和音频
对不上，而那种错误的症状是**音色像但吐字乱**，极难归因。

裁窗口的判据是**有声比例最高**而不是能量最大 —— 能量最大的那一段往往是一句
喊叫或大笑，那个语气会渗进之后所有的合成。

**转写出来一定要核对。** 它错了不会报错，只会让克隆吐字乱。

> macOS 上没法顺手建 `.txt`？Finder 和 TextEdit 默认给的是 `.rtf`
> （就是"MacOS 文稿"）。**代码认 `.rtf`**，会自动剥掉标记，所以直接存就行。
> 而用上面那个工具则完全不需要你建任何文本文件。

### 已经有音频 + 文字

1. 新建 `voice-library/<人名>/`，把音频和同名 `.lab` / `.txt` / `.rtf` 丢进去
2. 跑整理脚本：

   ```bash
   cd tools/voices && uv run --project ../f5-tts python organize.py
   ```

   它会把原始素材归到 `library/`、按可量化指标挑出几条命名好的参考，
   **已有的参考保留不动**。只整理某个人就加名字：`organize.py furina`

3. 重启服务：`./scripts/anima.sh restart`

### 体检

```bash
cd tools/voices && uv run --project ../f5-tts python organize.py check
```

不动任何文件，只报每条参考的时长、静音占比、以及**有没有被有损压缩砍掉高频**。

## 音频格式

`.wav` / `.mp3` / `.m4a` / `.flac` 都能用，**mp3 实测通过**（列表、合成、
Rust 与 Python 两侧都验过）。

但码率要够。实测同一条 48kHz 素材经 libsndfile 压缩：

| 质量 | 高频截断 | 对引擎有影响吗 |
|---|---|---|
| 最高（compression_level 0.0） | 无 | 无 |
| 中（0.5） | 16.5kHz | **无** —— 引擎用不到那么高 |
| 较低（0.9） | **8.0kHz** | **有** —— 8~12kHz 是齿音（s/sh/x/z），丢了声音发闷 |

引擎实际用得到的上限是 12kHz（F5-TTS 内部重采样到 24kHz）到 16kHz
（GPT-SoVITS 32kHz）。所以砍在 16kHz 无所谓，砍在 8kHz 就真丢内容。
`organize.py check` 会把这一条测出来 —— 判据是**找砖墙式断崖**而不是
"能量到哪儿为止"，后者会把女声天然的高频滚降误报成压缩损伤。

## 转写稿的三个坑

**`.lab` 有两种，只有一种能用。** 语音包里的 `.lab` 是纯转写稿（那句话本身），
能直接用；DiffSinger / NNSVS / UTAU 生态里还有一种同名的 HTK 标注，逐行是
"起时间 止时间 音素"。后者拿去当参考文本会让克隆完全跑偏，而症状是**音色像但
吐字乱**，极难归因。代码会判形状并拒收。

**macOS 的 RTF 也认。** Finder / TextEdit 默认产出的"MacOS 文稿"就是 RTF，
普通用户很难顺手建纯 `.txt`。代码会剥掉 RTF 标记，包括整组丢掉
`{\fonttbl…}` 这类元数据组 —— 只去花括号的话字体名会被当成句子的一部分。
判据看内容而不是扩展名，所以把 RTF 存成 `.txt` 也没事。

**游戏模板标记并没有被念出来。** 比如 `#早上好，{NICKNAME}。看你的气色…`：
`#` 是"这句带占位符"的标记，`{NICKNAME}` 在实际语音里是玩家名或干脆是停顿。
留着会让模型按错误的音素去对齐参考音频。代码会清掉 `#` 前缀、`{...}` 占位符和
`<...>` 富文本标签。

## 参考音频的选择标准

`organize.py` 按这些指标打分（都是实测踩出来的）：

| 指标 | 要求 | 为什么 |
|---|---|---|
| 时长 | 4~12 秒，最好 8 秒 | 太短抓不稳音色；太长会被 F5-TTS 截断，而且**参考长度直接加进每次合成的耗时** |
| 静音占比 | 越低越好 | 实测过一条 3.3 秒的，44% 是静音，有效内容不到 2 秒 |
| 削波 | 不允许 | 参考里的噪声会被一起克隆进去 |
| 语速 | 3~6 字/秒 | 太快太慢都不是好参考 |
| 动态范围 | 适中 | 排掉喊叫和大笑 —— 那个语气会渗进之后所有的合成 |

写出时统一转成 24kHz 单声道：48kHz 的数据量是两倍，而参考长度算进每次合成的
耗时；规格一致也让出问题时少一个变量。
